# NetCache

A small HTTP/1.1 caching proxy in C++17 with a deliberately narrow scope: `GET` only, one fixed
upstream, strict `Content-Length`/decoded chunked framing, bounded cache memory. The goal is correctness you can explain, not
feature count.

**Status: Phase 3 complete (strict chunked forwarding, policy-based eviction, and benchmark support).**

| Phase | Delivers | State |
|---|---|---|
| 1 | Hardened TCP/HTTP forwarding proxy, worker pool, load shedding, strict parser | done |
| 2A | Standalone bounded thread-safe LRU cache (`src/cache.*`), injectable clock | done |
| 2B | Proxy integration, eligibility rules, per-key request coalescing, opt-in stats | done |
| 3 | Chunked forwarding (uncached), cost-aware eviction, reproducible benchmarks | done |

## Build and test

```sh
cmake -S . -B build && cmake --build build -j
ctest --test-dir build --output-on-failure        # 5 unit suites + integration (Python)

cmake -S . -B build-asan -DNETCACHE_SANITIZE=address,undefined && cmake --build build-asan -j
cmake -S . -B build-tsan -DNETCACHE_SANITIZE=thread           && cmake --build build-tsan -j
```

`tools/verify.sh [--sanitize]` does the whole check in one command (CMake if present, otherwise direct `g++`).

## Run

```sh
python3 tools/origin.py --port 9000 &
./build/netcache --port 8080 --upstream-port 9000
curl -i http://127.0.0.1:8080/hello
# Compare a seeded workload with the default LRU or --eviction cost-aware:
python3 tools/bench.py --port 8080 --seed 20261020
```

`./build/netcache --help` lists every option. Cache-related ones:

| Option | Default | Meaning |
|---|---|---|
| `--cache-bytes N` | 16 MiB | hard budget for stored response bytes; `0` disables caching (everything is `BYPASS`) |
| `--cache-entry-bytes N` | 2 MiB | largest single stored response (head + body); bigger ones are forwarded, not stored |
| `--default-ttl-s N` | 60 | TTL for responses with no `Cache-Control`; `0` = cache only explicit `max-age` |
| `--max-ttl-s N` | 3600 | clamp applied to every TTL |
| `--coalesce-wait-ms N` | upstream timeout + 2000 | longest a request waits for another request's fetch |
| `--no-coalesce` | off | disable coalescing (control experiment) |
| `--eviction KIND` | `lru` | choose `lru` or `cost-aware` eviction |
| `--enable-stats` | off | serve JSON counters at `/__netcache/stats` |

Every response that came through the cache path carries one `X-Cache` header:
`HIT`, `MISS` (fetched and stored), `COALESCED` (shared another request's in-flight fetch),
`BYPASS` (not stored, or the request skipped the cache). Error pages (4xx/5xx generated by the
proxy) carry none. Anything under `/__netcache/` is never forwarded upstream: it is `404` unless
`--enable-stats` is set, in which case exactly `/__netcache/stats` is served locally.

## Architecture

```
accept (main thread) -> bounded queue -> N workers
worker: read head (deadline) -> parse/validate -> bypass check -> CoalescingCache::getOrFetch
          hit  -> stored bytes
          miss -> ONE owner per key runs fetchUpstream (no lock held); waiters share its result
        -> stamp X-Cache -> relay
```

| Module | Role | Knows about |
|---|---|---|
| `src/http.*` | strict parser, message builders | bytes only |
| `src/cache.*` | bounded LRU + TTL store (Phase 2A) | opaque key -> payload |
| `src/coalescing_cache.*` | single-flight over the cache, outcome enum | opaque payloads, a fetch callback |
| `src/cache_policy.*` | which requests/responses are eligible | Phase 1 HTTP types |
| `src/main.cpp` | sockets, worker pool, glue | everything |

* Fixed worker pool, blocking-style code over non-blocking sockets; every wait is `poll()` against
  an absolute deadline, so no peer can hold a worker longer than the configured timeouts.
* Full queue -> immediate `503` (load is shed, never queued without bound).
* The upstream response is fully read and validated **before** a byte is sent to the client, so a
  truncated or malformed upstream response can never be relayed as a success.
* `src/http.*` is pure (no I/O) and unit-tested byte-at-a-time; `src/main.cpp` owns sockets.

## HTTP contract (Phase 1)

Principle: reject ambiguity before forwarding; never repair framing.

**Requests:** `GET` + `HTTP/1.1` + origin-form target only. Rejected: dot segments (also
`%2e`), `%00`, fragments, backslashes, `//` prefix, bare CR/LF, obs-fold, whitespace before the
colon, control characters, missing/duplicate `Host`, any `Transfer-Encoding`, any non-zero or
duplicate `Content-Length`, `Expect`, `Upgrade`. Limits: 8 KiB head, 64 headers, 2048-byte target.
Statuses: 400/405/408/414/417/431/501/505.

**Upstream request** is rebuilt from scratch: fixed `Host`, `Connection: close`, and at most one
client `Accept`. Cookies, `Authorization`, `Accept-Encoding`, etc. are never forwarded.

**Upstream response:** exactly one valid `Content-Length`, one strict `Transfer-Encoding: chunked`,
or 204/304, within `--max-response-bytes`. Chunk extensions, trailers, duplicate or conflicting
framing, truncated bodies, and garbage status lines yield `502` (`504` on timeout). Chunked bodies
are decoded and sent with a generated `Content-Length`; they are never cached. Hop-by-hop headers
are stripped and extra bytes after a complete body are dropped.

## Cache engine (`src/cache.hpp/.cpp`)

Opaque `key -> payload` store; it does no HTTP parsing and makes no cacheability decisions.

* API: `get(key)`, `put(key, payload, ttl)`, `erase`, `clear`, `stats`, plus `check_invariants()`
  (O(n), for tests).
* Structure: `unordered_map<key, list::iterator>` + `std::list` (front = MRU). One mutex guards
  everything; `get` returns the payload **by value**, so eviction can never dangle a caller's data.
* Config: `max_bytes` (total payload budget, default 16 MiB), `max_entry_bytes` (per-entry cap,
  default 2 MiB, clamped to `max_bytes`). Clock is injectable (`std::function`, default
  `steady_clock`). TTL is per `put`.
* Rules: `ttl <= 0` or an over-limit payload is rejected; hits do not extend TTL; an entry is
  expired when `now >= deadline`; a rejected `put` still removes any old value under that key
  (never leave stale data readable after a failed update); huge TTLs saturate rather than overflow.
* Eviction: when a new entry does not fit, expired entries are reaped first (one O(n) sweep, only
  on that path), then the configured policy evicts entries until it fits. `LruPolicy` is the default;
  `CostAwarePolicy` scores recency, measured fetch cost, and payload size with deterministic ties.
* Complexity: `get`/`erase` O(1) average; `put` O(1) average plus O(k) for k evictions.

Limitations of the store: the budget counts **payload bytes only** (keys, list/map nodes and allocator overhead
are extra, so many tiny entries use far more RAM than `max_bytes`); expiry is lazy (dead entries
hold budget until looked up or swept); `get` copies the payload; one global lock; no stale
serving. What is stored is the complete serialized client response
(status line + headers + body), so headers count against the budget.

## Caching rules (`src/cache_policy.*`)

Cache only what is explicitly eligible; anything unrecognised, malformed or ambiguous is
uncacheable. This is a small, deliberate subset of RFC 9111, not an implementation of it.

* **Key:** `GET | upstream authority | len:Accept | target-as-received`. The target is never
  decoded or normalised. `Accept` is in the key because it is the one client header forwarded
  upstream. Phase 1 already rejects ambiguous targets, so the key cannot be steered by them.
* **Request bypass** (forwarded, never stored, no coalescing, `X-Cache: BYPASS`): `Authorization`,
  `Proxy-Authorization`, `Cookie`, `Range`, any `If-*` conditional, `Cache-Control`, `Pragma`.
  (The upstream request is rebuilt without these anyway; bypass keeps personalised traffic out of
  shared state, which also keeps result-sharing between coalesced requests safe.)
* **Response must have:** status `200`; `Content-Length` framing; stored size <= entry limit; and none
  of `Set-Cookie`, `Set-Cookie2`, `Vary`, `WWW-Authenticate`, `Age`, `Pragma`, `Content-Range`.
* **`Cache-Control`:** at most one header; only `public`, `max-age=N`, `must-revalidate` (we never
  serve stale). `no-store`, `no-cache`, `private`, `s-maxage`, `stale-*`, `immutable`, unknown or
  malformed directives, duplicates, `max-age=0` => not cached. `Expires` alone is unsupported
  (not cached); with `max-age` it is ignored.
* **TTL:** `max-age`, else `--default-ttl-s`, clamped to `--max-ttl-s`.
* Errors (4xx/5xx, 502/504 we generate) are never cached, and neither is anything truncated or
  malformed: those never reach the cache layer.

## Request coalescing (`src/coalescing_cache.*`)

Per-key single-flight. The first miss becomes the **owner** and fetches; concurrent requests for the
same key wait and share its result. Different keys never wait on each other, hits never take the
coalescer lock, and **no lock is held during upstream I/O**.

* Expired entries are misses, so a refresh is coalesced the same way. Stale data is never served.
* If the owner fails (upstream error, timeout, exception of any type), **every waiter gets the same
  failure** (`502`/`504`), nothing is cached, and the key is released so the next request retries.
  One RAII guard publishes the result, erases the in-flight record and wakes all waiters on every
  exit path. Waiters also have their own deadline (`WaitTimeout` -> `504`).
* On shutdown, waiters are woken (`503`) and no new fetches start; fetches already running finish.
* The owner stores into the cache *before* unregistering, and a thread that finds no in-flight record
  re-checks the cache under the coalescer lock, so a finished fetch is never repeated.
* Lock order is coalescer mutex -> cache mutex, never the reverse; the cache never calls back out.
* Outcome -> HTTP: `Hit`/`MissStored`/`MissUncacheable`/`Coalesced` -> the response with
  `HIT`/`MISS`/`BYPASS`/`COALESCED`; `UpstreamFailure` -> 502; `UpstreamTimeout`/`WaitTimeout` -> 504;
  `Cancelled` -> 503.
* A valid but uncacheable result (a 404, a `no-store` page) *is* shared with requests that are in
  flight at the same moment, but never stored. That is only safe because personalised requests
  bypass the cache entirely.

### Verified results (Phase 2B)

Linux, g++ 13.3, `-std=c++17 -Wall -Wextra -Wpedantic -Wshadow`, zero warnings. **CMake/CTest were not
available in the sandbox**, so `CMakeLists.txt` is written but not build-tested; every target was built
directly with `g++` using the same flags and sources, and `integration_test.py` was run as CTest would
run it (`python3 tests/integration_test.py <netcache binary>`).

| Check | Plain | ASan+UBSan | TSan |
|---|---|---|---|
| `http_test` (24: 18 Phase 1 + 6 new) | pass | pass, no reports | 0 warnings |
| `cache_test` (20) | pass | pass, no reports | 0 warnings |
| `coalescing_test` (19) | pass | pass, no reports | 0 warnings |
| `cache_policy_test` (8) | pass | pass, no reports | 0 warnings |
| `integration_test.py` (46: 19 Phase 1 + 27 new), proxy built with the sanitizer | 46 pass | 46 pass, 0 report files | 46 pass, 0 report files |

Sanitizer reports for the proxy subprocess were captured with `ASAN_OPTIONS/UBSAN_OPTIONS/TSAN_OPTIONS=log_path=...`
(the test harness discards the proxy's stderr); the capture was checked against a deliberately racy program.

What the integration tests assert (against the origin's own request counters, not just `X-Cache` labels):
repeat requests hit the origin once; 50 simultaneous misses cause exactly 1 origin fetch (one `MISS`, rest
`COALESCED`); the same burst with `--no-coalesce` reaches the origin many times (control experiment);
different keys and different `Accept` values do not collide; TTL expiry refetches and never serves stale; an
expired-entry burst causes exactly one refresh; 13 ineligible response kinds and 5 personalised request kinds
bypass the cache and reach the origin every time; oversize and over-budget cases keep stored bytes <= budget
with the LRU victim chosen correctly; owner failure (truncated and reset upstream) and upstream timeout wake
all 20/10 waiters with 502/504 and release the key; cached entries survive the origin being killed; SIGTERM
with waiters in flight exits promptly.

## Measured Phase 3 benchmark

The following numbers were measured on 2026-10-20 in the Linux build using
`tools/bench.py`, three seeded runs per configuration, 200 sequential requests per run, 20 keys,
64 workers, a 5,000-byte cache budget, and a 1,000-byte per-entry limit. The origin and proxy ran
locally in the same Linux environment; these are comparative application measurements, not
cross-machine production capacity claims.

| Configuration | Mean latency | p95 latency | Serial-equivalent req/s* | Cache hits | Errors |
|---|---:|---:|---:|---:|---:|
| LRU | 0.522 ms | 1.219–1.846 ms | ~1,916 | 531/600 (88.5%) | 0 |
| Cost-aware | 0.448 ms | 1.008–1.701 ms | ~2,232 | 538/600 (89.7%) | 0 |
| LRU, coalescing disabled | 0.557 ms | 1.487–1.972 ms | ~1,795 | 531/600 (88.5%) | 0 |
| Cache disabled | 1.267 ms | 1.640–1.927 ms | ~789 | 0/600 (0%) | 0 |

Across the three runs, cached LRU traffic was approximately 2.4x faster by mean latency than the
cache-disabled control. The cost-aware result was directionally better in this workload, but the
workload did not vary upstream fetch cost enough to establish a general policy advantage; treat the
policy comparison as an implementation demonstration, not a statistically significant benchmark.
The benchmark reports `mean_ms`, `p95_ms`, labels, request count, seed, and failures as JSON so the
same workload can be reproduced with `--seed`.

\* `req/s` is the reciprocal of mean per-request latency for this sequential benchmark
(`1000 / mean_ms`); it is not a concurrent throughput ceiling.

Seeded-bug check on `coalescing_cache.cpp` (6 mutants): no cache re-check before becoming owner, no
`notify_all`, in-flight record never erased, exceptions escaping the fetch, "stored" reported without
storing, waiter count never decremented. Each is caught (the missing `notify_all` shows up as a hang/timeout,
the escaping exception as an abort). The first run showed the re-check mutant *surviving*, which is why
`owner_finishing_between_first_lookup_and_registration_is_not_refetched` and its test seam
(`Options::after_first_miss`) exist.

Validation completed in the Linux toolchain: CMake build, all five unit executables, and the Python
integration suite passed. The benchmark harness was run for LRU, cost-aware, no-coalescing, and
cache-disabled controls. IPv6 and non-Python origins remain untested.

## Known limitations (honest list)

* IPv4 listener only; Linux only (`accept4`, `MSG_NOSIGNAL`).
* `Connection: close` on both sides, so no keep-alive, and `HTTP/1.0` clients are rejected.
* Responses are buffered whole: worst-case in-flight memory is `workers x max-response-bytes`,
  plus the cache budget, plus per-entry metadata (keys, nodes, allocator overhead) that the budget
  does not count. The cache limit is therefore a limit on cached payload, not on process RSS.
* **Waiters occupy workers.** A coalesced request blocks its worker for up to the fetch time, so
  many waiters on one slow key can starve unrelated requests when `--workers` is small. Size the
  pool above the expected fan-in. This is the main cost of the thread-pool model.
* One owner failure fails all of its waiters at once (no retry), by design.
* A `HIT` copies the stored response out of the cache (one memcpy of up to the entry limit).
* One global cache lock; `put` can do an O(n) sweep of expired entries when the cache is full.
* Expiry is lazy: dead entries hold budget until looked up or swept. No `Age` header is emitted.
* No `HEAD`, revalidation (`If-None-Match`), `Vary` handling, or stale-while-revalidate.
* Shutdown with the cache on: queued requests that would need a *new* upstream fetch get `503`
  while draining; hits are still served.
* A worker is occupied for the whole upstream fetch (and up to 200 ms of lingering close), so
  slow upstreams reduce capacity. Size `--workers` accordingly. This is the main cost of the
  thread-pool model and the motivation for an `epoll` variant.
* Graceful shutdown drains queued connections; it can take up to the request timeout if a client
  holds a connection open without sending anything.
* Duplicate `Content-Length` headers are rejected even when identical (stricter than the RFC).
* Under overload, a shed client may see a connection reset instead of the `503` (best effort).
* `%2f` in paths is not rejected; since the proxy forwards the target verbatim, this is a
  question for the origin, not a proxy-side ambiguity.
